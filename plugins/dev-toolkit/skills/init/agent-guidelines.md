## 设计协作准则

`docs/design/` 中标记为“已确认”的内容构成当前设计基线；草稿、待确认或需修订内容只作为参考。处理涉及设计的开发任务时遵循：

1. **改码先查设计**：修改需求行为、业务规则、组件边界、接口、数据结构或关键交互前，先阅读 `docs/design/README.md` 和相关设计条目；“需修订”的内容不得继续当作有效约束。
2. **适用时携带编号**：存在对应设计编号时，在任务说明以及用户要求创建的 commit 中携带编号，例如 `FR-003`、`UC-002` 或 `CMP-002`；没有对应编号时不臆造。
3. **偏差不得静默实现**：发现实现条件与已确认设计冲突时，先向用户说明冲突证据、受影响编号和建议。获得设计修改授权后，先更新事实来源并把受影响阶段标记为“需修订”；设计重新确认前，不把偏差写成既定结论。
4. **按需维护工作摘要**：仅当本次开发修改了设计文档，或产生了等待确认的设计问题时，在 `docs/design/README.md` 的“最近工作摘要”追加一行，记录日期、改动或问题、受影响编号以及下一步。
5. **新需求先进设计**：新的功能需求、业务规则或架构方向先进入 `docs/design/` 修订流程，确认并恢复受影响阶段的一致性后再实现，不直接以代码替代设计决策。

设计文档的状态、编号规则和目录结构见 `docs/design/README.md` 及各阶段文档。
