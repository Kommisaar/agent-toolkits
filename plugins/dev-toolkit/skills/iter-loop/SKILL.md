# Iter Loop 持续迭代协调器

## 目标与版本边界

作为 coordinator 运行：

**发现候选 → 选择任务 → 隔离派发 → 审查验证 → 线性合并 → 滚动补位 → 汇报**

协调器负责决策、Git 集成与验收，优先将探索、实现、独立门禁和独立审查分别委派给
`iter-scout`、`iter-builder`、`iter-verifier` 和 `iter-reviewer`。

v0.3.3 将协调状态保存到目标仓库的 `auto-iter/runs`，并支持显式 `/iter-resume`。状态
持久化不代表后台 Agent 会跨会话存活，也不会自动唤醒、重试、部署或修改外部项目管理
系统；恢复时必须重新核对 Git 现场。

v0.3.4 支持项目 `AGENTS.md` 声明的 worktree 池：开工时检查，未声明时询问添加；池位
固定命名并跨任务复用依赖，任务标识只体现在分支名。状态目录更名为 `.auto-iter/runs`；
滚动补位改为完成通知驱动，禁止凑批次等待。

v0.3.5 池位生命周期改为跨 run 保留：run 结束只注销台账登记并留痕，物理移除须用户
明确要求；恢复与新 run 优先接管现存池位与依赖。worktree 池成为唯一派发模式，默认
位于主树同级 `<仓库名>-iter/pool/`。

## 策略选择与优先级

每轮只选择一套运行策略，并在任何仓库修改前阅读对应文件：

- [`conservative`](strategies/conservative.md)：稳定性优先，不改变对外行为；
- [`balanced`](strategies/balanced.md)：质量与已有路线图小切片均衡；
- [`feature`](strategies/feature.md)：围绕用户明确授权的功能目标推进。

用户没有指定策略时，使用结构化选择题询问。陌生仓库、目标不明确或只要求“加固”时推荐
`conservative`；日常维护推荐 `balanced`；只有目标与验收方向明确时才提供 `feature`。

策略只填补用户没有指定的值，不能扩大授权。按以下顺序处理冲突：

1. 平台限制、适用的仓库强制约定和本 Skill 的不可违反安全边界；
2. 用户对本轮明确给出的目标、预算、排除项和确认结果；
3. 所选策略的默认值。

高优先级约束冲突或无法同时满足时进入 `PAUSED`，不得静默选择较宽松的一方。

## 技术栈识别

根据仓库证据选择零个或多个技术栈包：

- [`typescript`](stacks/typescript.md)：TypeScript、JavaScript 和 Node.js；
- [`frontend-web`](stacks/frontend-web.md)：浏览器 UI、SSR、组件与 E2E；
- [`python`](stacks/python.md)：Python 应用、库和服务；
- [`rust`](stacks/rust.md)：Cargo crate 与 workspace；
- [`java`](stacks/java.md)：Maven、Gradle 和 JVM 项目；
- [`react`](stacks/react.md)：React 组件、Hooks、StrictMode 和 hydration；
- [`tauri`](stacks/tauri.md)：Tauri 2 桌面/移动应用及跨语言边界。

技术栈包可以组合，例如前端 TypeScript 项目同时读取 `typescript` 和 `frontend-web`。
Tauri React 项目组合 `tauri`、`rust`、`typescript`、`frontend-web` 和 `react`。
它们只补充工具链识别、门禁和生成物注意事项，不改变运行策略、用户授权或项目约定。

选择依据依次为仓库文档、CI、构建清单、锁文件和源码。技术栈包推荐与项目脚本冲突时，
始终使用项目脚本并记录差异；证据不足时不猜测。

## 启动契约

开始修改前确认以下信息：

1. **运行策略**：`conservative`、`balanced` 或 `feature`。
2. **技术栈包**：根据仓库证据选择，可多选。
3. **目标仓库**：当前工作区中的 Git 仓库。
4. **迭代目标**：用户目标、仓库路线图，或“以低风险加固为主”。
5. **运行预算**：截止时间和时区、最大任务数、单批次，或用户明确授权“直到我叫停”。
6. **排除项**：禁止触碰的目录、功能或变更类型。
7. **风险边界**：是否允许用户可见行为、公共接口或依赖发生变化。

缺少目标时，默认只寻找证据充分的缺陷、测试盲区、文档错误和小范围技术债。缺少运行
预算时采用所选策略的 `default-task-budget`，并在开工前展示；不得自行进入无限循环。

生成并展示“本轮运行卡”：

```text
策略:
技术栈包:
状态: RUNNING
Run ID 与状态路径:
目标与依据:
预算、时区与派发截止点:
集成分支与基准 SHA:
允许范围:
排除项:
自动执行风险上限:
必须确认事项:
默认与最大并发:
完整门禁与基线结果:
```

运行卡中的仓库信息和门禁结果在开工审计后补齐。目标、策略或风险边界仍有实质歧义时先
询问，不得派发 builder。

## 持久状态

任何写操作前阅读并遵守[状态协议](references/state-protocol.md)，使用本 Skill 自带的
`scripts/state_store.py`。根据当前 `SKILL.md` 的实际位置解析脚本绝对路径；不要把脚本
复制到目标仓库，也不要自行实现另一套状态格式。

状态固定保存在：

```text
<repo-root>/.auto-iter/runs/
```

首次初始化由状态助手通过 `git rev-parse --git-common-dir` 定位并幂等更新
`.git/info/exclude`，只加入 `/.auto-iter/runs/`。初始化失败、路径下存在已跟踪文件、
目录解析到仓库外或 ignore 规则无法确认时进入 `PAUSED`。

只有 coordinator 可以写状态。所有子 Agent 的禁止修改范围必须包含
`<repo-root>/.auto-iter/runs/**`；状态中不得保存密钥、完整源码、用户数据或不必要的完整
日志。

每次状态转换、任务派发与完成、分支/worktree/commit 确定、门禁结束、审查结论、合并和
资源清理后，立即调用状态助手落账。助手写入失败时暂停继续派发或合并，避免实际 Git
状态继续领先于记录。

## 运行状态

- `RUNNING`：发现、派发和补充任务。
- `DRAINING`：不再派发新任务，只处理用户允许收尾的在飞任务。
- `PAUSED`：遇到需要用户决策或无法安全继续的阻塞；这不是完成。
- `STOPPED`：用户要求停止，或预算耗尽且已完成安全收尾。

状态转换规则：

- `/iter-status` 读取持久状态并与实际 Git 做只读对账，不改变运行状态。
- `/iter-resume` 不信任旧会话或旧 Agent；先按状态协议对账，安全后才恢复协调。
- 用户调用 `/iter-stop` 且存在在飞任务时，询问“安全收尾”或“立即停止”；无在飞任务时
  直接停止。
- 用户说“停止派活”“开始收尾”或在 `/iter-stop` 中选择“安全收尾”时进入 `DRAINING`。
- 用户说“立即停止”或在 `/iter-stop` 中选择该项时，不再进行任何新修改；在工具支持时
  中断后台任务，保留分支并汇报。
- 到达派发截止点后进入 `DRAINING`。只有预计实现、审查、完整门禁和合并都能在剩余预算
  内完成时，才可派发新任务。
- 脏集成工作树、权限/认证失败、无法运行必要门禁、重大产品或架构决策、不可逆操作，
  均进入 `PAUSED` 并提出一个明确问题。

## 不可违反的安全边界

1. **保护用户工作**：不得 reset、清理、覆盖、丢弃或私自 stash 用户改动。集成工作树
   不干净时暂停。
2. **不写死主分支名**：以启动时用户所在且准备接收改动的分支作为集成分支，记录其名称
   与基准 SHA。detached HEAD 或目标不明确时先询问。
3. **主工作树只做集成**：业务修改必须发生在本轮创建的 worktree；主工作树只执行
   ff-only 合并、必要验证和状态检查。
4. **无外部副作用**：不得 push、发布、部署、发消息、修改远端资源、处理真实数据或读取
   未获授权的凭据。
5. **高风险必须确认**：数据库迁移、数据删除、认证授权、密钥与权限、破坏性公共接口、
   大版本依赖升级、许可证变化和不可逆生成操作都先暂停确认。
6. **不虚构产品需求**：没有仓库证据或用户授权时，不新增用户可见功能，不自行决定重大
   产品行为。
7. **只清理自有资源**：只删除台账中登记为本轮创建或接管、且已确认干净的 worktree
   和分支；跨 run 保留的池位仅在用户明确要求时移除。
8. **状态目录由 coordinator 独占**：子 Agent 不得读写运行状态，状态目录不得成为业务
   修改或提交的一部分。

## 开工审计

派发实现任务前完成一次预检：

1. 阅读仓库根及相关目录中的 `AGENTS.md`、`CLAUDE.md`、`README`、贡献指南和设计文档。
2. 确认 Git 仓库、集成分支、基准 SHA、工作树状态和已有 worktree；工作树不干净即暂停。
3. 确定池配置：仓库 `AGENTS.md` 声明 worktree 池（池目录、池位数与取用回池规则）
   时以其为准；未声明时使用默认位置——主树同级 `<仓库名>-iter/pool/`，池位数为
   最大并发。可询问用户是否把池说明写入 `AGENTS.md` 以便后续 run 直接复用；写入仅
   持久化配置，不改变本轮行为。池说明至少包含：池目录（默认主树同级
   `<仓库名>-iter/pool/`，可声明其他同盘位置覆盖）、固定命名的池位（数量为最大
   并发）、取用与回池规则、池位跨 run 保留（仅用户明确要求或确认不再迭代时物理
   移除）。
4. 根据构建清单、锁文件和源码选择适用的技术栈包，读取后再解析项目实际命令。
5. 从项目文档、CI 配置、包管理脚本和语言工具链中识别完整门禁，包括适用的：
   - 格式或生成物检查；
   - lint；
   - 类型检查或编译；
   - 单元、集成或端到端测试。
6. 使用状态助手初始化运行，用重复的 `--stack` 记录每个技术栈包，并记录策略、目标、
   预算、风险、并发、集成分支、基准 SHA 和完整门禁命令；把返回的 Run ID 与状态路径
   补入运行卡。
7. 在基准分支运行一次完整门禁，并逐项写入 `baseline` 门禁记录。记录命令、退出状态和
   既有失败，后续不得把既有失败
   误报为本轮引入，也不得接受新增失败。
8. 从所选策略读取默认与最大并发，再根据机器资源和项目规模向下调整；任何策略下都不得
   超过 4。共享 schema、锁文件、公共配置、生成物或核心接口的任务必须串行。
9. 将持久状态作为唯一运行台账；会话摘要只是视图，发生冲突时以 Git 现场和成功写入的
   状态记录共同判断，不得仅凭对话继续。

若基准门禁失败，只有范围明确且可验证时才把失败本身列为修复任务；其他任务以
“不新增失败”为最低要求，并在每次汇报中保留基线失败。

## 候选生成与价值门槛

按所选策略限定候选类型和风险阈值，再调用 `iter-scout` 做只读审计。候选来源包括：

- 已确认缺陷、失败门禁、TODO、路线图和审计遗留；
- 测试盲区、契约漂移、错误处理和边界条件；
- 性能、可访问性、兼容性和安全加固；
- 死代码、重复定义、过期抑制、文档或配置漂移。

每个候选必须包含：

- 可定位的证据；
- 预期收益与不做的影响；
- 预计文件和语义影响面；
- 风险、规模与依赖关系；
- 可判定的验收条件和验证命令。

优先选择“收益明确、证据充分、范围小、可独立验证、可回滚”的任务。仅文件不重叠不代表
任务独立；共享符号、协议、schema、配置和锁文件也视为冲突面。

若没有达到价值门槛的候选，可再做一次不同角度的只读审计；仍无结果时进入 `PAUSED`，
说明已检查范围和证据。不得为了保持循环而制造无意义改动。

## 任务派发

每个实现任务独占一个池位并使用独立分支，worktree 池是唯一的派发模式：池目录默认为
主树同级的 `<仓库名>-iter/pool/`（同级位置天然同盘；`AGENTS.md` 声明的池目录优先）。

- run 启动时建立固定池位：按池说明固定命名（如 `wt-1..N`，N 为最大并发），逐位确认
  `git status` 干净后一次性登记台账。池位可能跨 run 存在：优先接管现存池位——
  detached 且干净的直接接管登记；带遗留分支或脏状态的逐一报告并询问，不得自动
  清理或删除分支；缺失的才新建。
- 任务分配空闲池位：取用时以集成分支最新提交创建任务分支，任务标识只体现在分支
  名；派发落账必须写明该任务占用的池位绝对路径。
- 任务完结后先将池位 `checkout --detach` 脱离任务分支，再删除该分支——顺序不能
  反，分支仍被 worktree 占用时删除会被拒绝；`node_modules` 与工具缓存原样保留供
  后续任务复用。
- run 结束（预算到点、候选枯竭或用户停止）时保留池位与依赖：注销台账登记并留
  event 写明各池位状态；物理移除仅在用户明确要求清理或确认项目不再迭代时执行；
  不得对池位执行 `git clean -xdf`——依赖与工具缓存是池位资产。

派发 `iter-builder` 时必须给出完整任务包：

```text
Task ID:
运行策略与风险阈值:
技术栈包:
目标与证据:
集成分支与基准 SHA:
worktree 绝对路径与任务分支:
允许修改:
禁止修改:
验收条件:
Builder 任务级门禁:
Verifier 完整门禁、超时与允许生成物:
已知基线失败:
风险与截止预算:
报告格式:
```

同时明确：

- 严格限制在指定 worktree 内工作；
- 先阅读项目约定；
- 只处理一个任务，不扩张范围；
- 只提交、不 push，不 pull/rebase/merge 集成分支；
- 不修改协调台账；
- 不读取或修改 `.auto-iter/runs`；
- 如实报告偏离、失败和最终 commit SHA。

实现代理在后台运行。不要无依据轮询后台子代理；利用完成通知，并在等待期间进行不冲突的
审计或审查工作。派发前将任务、分支和 worktree 写入状态；收到完成通知后记录实际状态
和 commit SHA，再进入审查。

同一 worktree 同一时间只能由 builder、verifier 或 coordinator 中的一个写入或执行可能
产生文件的命令。不得在 builder 仍运行时启动 verifier。

## 审查、验证与合并

每个任务逐一执行以下流程：

1. 核对 builder 报告、任务分支状态、提交和实际 diff；报告不是证据。
2. 检查范围漂移、意外生成物、锁文件和未提交内容。发现越界则退回修正，不得顺手接受。
3. 由 coordinator 将任务分支 rebase 到集成分支最新提交。只可直接解决纯机械冲突；
   涉及行为选择时退回 builder 或暂停请求决策。
4. 调用 `iter-verifier` 在 rebased 任务 worktree 中运行完整门禁，并与开工基线比较。
   Verifier 不可用时由 coordinator 执行完全相同的命令。`FAIL`、`BLOCKED`、
   `CONTAMINATED` 或新增失败均不得合并；协调器核对实际 Git 状态和命令证据。
5. 调用 `iter-reviewer` 独立审阅最终 diff、任务验收条件、技术栈风险和门禁证据。
   `REQUEST_CHANGES`
   必须修复后重新从第 1 步检查。
6. 合并前再次确认主工作树干净、集成分支名称正确且 HEAD 未发生意外变化。
7. 使用 `git merge --ff-only` 合并。禁止强推、merge commit 和未经授权的历史重写。
8. 合并后检查状态，执行必要的快速冒烟验证，把任务标记为 `MERGED`，并在集成工作树
   干净时调用 `sync-head` 记录最新 HEAD。
9. 仅在 worktree 干净、提交已合并且路径所有权明确时清理；删除本轮任务分支前再次
   确认其提交已包含在集成分支中。清理只做任务级回收：池位 `checkout --detach`
   后删除任务分支，池位本身保留供后续任务或后续 run 复用。
10. 每一步完成后同步任务状态、门禁记录和自有资源；在状态落账成功前不派发补位任务。

任何生成物差异都按真实内容审查。不得用覆盖式 Git 命令把无法解释的差异直接抹掉。

## 滚动补位

当一个并发槽位释放时，而不是等所有任务清空后：

1. 更新集成分支、剩余预算和在飞任务影响面；
2. 重新排序候选；
3. 仅在有足够实现与集成缓冲时补充一个不冲突任务；
4. 候选不足时再次调用 scout，而不是重复派发相同审计。

完成通知到达即执行上述补位流程；存在无冲突候选且缓冲足够时必须立即派发，禁止为
凑批次等待其他在飞任务，也不得以等待期间的审计或审查为由推迟补位。

保持小批量在飞，优先快速完成和集成，避免同时积压大量基于旧基线的分支。

## 汇报

只报告有证据的事实。每次阶段汇报至少包含：

- 当前状态与剩余预算；
- 已合并任务和 commit SHA；
- 在飞任务、分支及影响面；
- 门禁命令、结果和既有失败；
- 被拒绝或暂停的任务及原因；
- 下一步候选。

最终总结必须区分“已合并”“已完成但未合并”“被阻塞”“未开始”。说明状态保存路径，
并明确会话结束后 Agent 不会继续运行；下一次必须由用户显式调用 `/iter-resume`。
