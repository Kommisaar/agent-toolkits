# Conservative 保守加固

## 适用场景

用于稳定性优先、维护窗口、陌生仓库或用户没有给出明确产品目标的迭代。目标是在不改变
对外行为的前提下，修复证据充分的问题并提高可验证性。

## 默认运行策略

- 未指定任务预算时，以“一批、最多合并 2 个任务”为默认预算。
- 默认并发 1；仅当任务的文件与语义影响面明确独立时提升到 2。
- 只自动执行 `low` 风险任务；`medium` 和 `high` 风险均暂停确认。
- 每个任务保持小而完整，应能由一个 builder 独立实现、验证和提交。
- 完整基线门禁、任务级测试、合并前完整门禁和独立 reviewer 均不可省略。

## 可自动选择

- 已复现缺陷和现有失败门禁；
- 测试盲区、边界条件和 mock/实现漂移；
- 文档、注释和配置说明与现状不一致；
- 死代码、重复定义、过期抑制和范围明确的小重构；
- 有基准证据且不改变行为的局部性能修复。

## 默认禁止

- 新增或改变用户可见行为；
- 修改公共 API、schema、序列化格式或兼容性承诺；
- 新增依赖、升级依赖或改写锁文件；
- 跨模块架构调整、批量重写和大范围格式化；
- 数据迁移、认证授权、部署、远端资源和真实数据操作。

命中禁止项时，不得自动退化为“顺手修改”；应改为候选并请求用户选择其他策略或单独授权。

## 排序偏好

1. 数据损坏、安全和明确正确性问题；
2. 构建、类型、lint 和测试失败；
3. 能防止回归的测试补强；
4. 文档与配置漂移；
5. 有证据的小范围技术债。

## 完成标准

- 不新增用户可见行为和外部契约变化；
- 没有未经授权的依赖或生成物变化；
- 任务验收条件与完整门禁均有实际证据；
- reviewer 没有 `MEDIUM` 及以上未解决发现；
- 最终 diff 可独立解释并可安全回滚。
