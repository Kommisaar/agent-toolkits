# Feature 功能推进

## 适用场景

用于用户已经给出明确功能目标、验收方向或仓库存在已批准设计的场景。策略目标是把功能
切成可独立验证的小片段，而不是授予协调器自由创造产品需求的权限。

没有明确功能目标时不得选择本策略；应改用 `balanced`，或暂停询问用户。

## 默认运行策略

- 未指定任务预算时，以“一个功能切片、最多合并 2 个实现任务”为默认预算。
- 设计和契约未稳定前默认并发 1；确认任务真正独立后最多并发 2。
- 只自动执行已批准功能边界内的 `low` 风险实现；超出边界或达到 `medium` 风险时暂停。
- 第一个实现任务派发前必须形成设计备忘，并完成开放问题处理。
- 完整基线门禁和合并前完整门禁不可降低；新行为必须有相应自动化测试或明确的替代证据。

## 设计备忘

设计备忘保留在当前会话，除非用户或项目约定要求写入仓库。至少包含：

- 目标、用户价值和成功条件；
- 非目标与明确排除项；
- 当前行为和可定位依据；
- 交互、接口、数据、权限和兼容性影响；
- 实现切片及依赖顺序；
- 测试、回滚和发布风险；
- 需要用户裁定的开放问题。

开放问题没有证据支持唯一安全答案时必须询问用户，不得以“推荐方案”代替授权。

## 可自动选择

- 已批准功能的内部实现和测试；
- 为该功能补齐的错误处理、可访问性和兼容性；
- 实现前必要且范围明确的契约或测试夹具整理；
- 与功能直接相关、保持向后兼容的局部重构；
- 支持验收所需的文档和示例。

## 必须确认

- 目标、非目标或验收标准发生变化；
- 用户流程、默认值或可见行为出现设计备忘之外的变化；
- 公共 API、schema、序列化格式或兼容性承诺变化；
- 数据迁移、认证授权、密钥、许可证和大版本依赖升级；
- 新增第三方服务、生产配置、部署或远端资源操作；
- 无法自动验证的关键行为。

## 切片规则

1. 先建立可验证的最小纵向切片，避免按技术层堆积长期无法验收的分支。
2. 公共契约或共享基础必须先串行稳定，再并发处理独立调用方。
3. 每个 builder 只接收一个可提交、可回滚的任务。
4. 后续切片以上一切片已经合并的集成分支为基线。
5. reviewer 除代码正确性外，还要核对设计备忘和用户验收条件。

## 完成标准

- 功能行为与设计备忘、用户授权和验收条件一致；
- 所有开放问题均已解决或明确排除；
- 新行为有实际测试或经用户接受的替代验证；
- 没有设计边界外的接口、数据、权限或依赖变化；
- 每个合并提交都可独立解释，最终切片可演示且可回滚。
