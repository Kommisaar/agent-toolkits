# 阶段 03：领域模型

## 阶段目标

建立开发者与业务人员共享的业务概念模型，明确关键对象、关系、不变量、业务过程和状态生命周期。

该阶段描述业务世界，而不是数据库表、ORM 实体、接口 DTO 或框架类。可以使用实体、值对象、聚合等术语，但只有在它们帮助表达业务边界时使用，不强制套用 DDD。

## 进入阶段前

确认或读取：

- 术语表；
- 功能需求和业务规则；
- 关键用例规约；
- 用例中的输入、输出、状态变化和失败结果；
- 现有数据字典或旧系统模型，仅作为证据。

## 概念发现

从用例和规则中识别：

- 具有稳定身份、会随时间变化的业务对象；
- 通过属性值定义、可以替换的值对象；
- 描述分类、策略、资格或状态的概念；
- 业务事件及其发生时间；
- 外部系统提供但本系统需要引用的概念；
- 必须一起保持一致的对象边界候选。

不要机械提取所有名词。页面、按钮、请求、响应、管理器等技术词通常不是领域概念。

## 访谈顺序

### 身份与生命周期

- 哪些业务对象需要区分“同一个”？
- 对象从创建到结束经历哪些阶段？
- 删除代表物理删除、作废、归档还是状态变化？
- 谁创建、拥有、转移或关闭对象？

### 关系与数量

- 对象之间是什么业务关系？
- 关系是否有时间范围、角色或自身属性？
- 一方可以关联多少个另一方？
- 关系断开后数据和业务含义如何变化？

### 不变量与边界

- 哪些条件在任何成功操作后都必须成立？
- 修改一个对象时必须同时检查或修改哪些对象？
- 哪些规则只能由一个明确边界负责保证？
- 哪些信息来自外部，只能缓存或引用而不能自行修改？

### 状态与事件

- 什么业务事件触发状态变化？
- 哪些转换被禁止？
- 失败、超时、取消和补偿会进入什么状态？
- 状态变化是否需要审批、审计或通知？

### 时间与历史

- 规则使用当前值还是发生时快照？
- 是否需要保留历史版本、变更原因或有效期？
- 延迟事件和乱序事件如何影响业务判断？

## 概念条目

`domain-model.md` 使用 [templates/03-domain-model/domain-model.md](templates/03-domain-model/domain-model.md)，包含概念总览类图骨架和概念条目结构。

不必为模型中的每个简单值都分配 `DOM-*`，编号用于需要跨文档追踪的重要概念和规则承载点。

## 领域类图

使用 Mermaid classDiagram 表达概念、主要属性和关系，骨架见模板。

约定：

- 使用业务名称，不使用数据库复数表名。
- 只展示对当前讨论有价值的属性和行为。
- 关系标签写业务含义。
- 基数无法确认时标记为待确认，不猜测。
- 领域图中的方法表示业务行为，不展开技术方法签名。
- 图后补充图无法完整表达的不变量、所有权和时间规则。

## 业务过程

跨多个对象或角色的业务过程使用 [templates/03-domain-model/business-processes.md](templates/03-domain-model/business-processes.md) 的结构，重点表达：

- 触发事件；
- 业务决策；
- 关键状态变化；
- 人工和系统责任；
- 补偿或终止路径。

不要把每个用例都重复绘制成业务过程图。

## 状态模型

具有复杂生命周期的概念使用 stateDiagram-v2，骨架和转换规则表见 [templates/03-domain-model/state-models.md](templates/03-domain-model/state-models.md)。

状态图旁必须说明：

- 转换的业务条件；
- 执行转换的角色；
- 转换产生的事件或副作用；
- 并发、重复命令和非法转换如何处理。

## 阶段完成判断

准备进入门禁前确认：

- 用例中的主要业务概念已定义；
- 术语在需求、用例和领域模型中一致；
- 关键关系、身份和所有权可解释；
- 重要业务不变量有明确承载点；
- 复杂生命周期具有状态和转换规则；
- 模型没有混入不必要的数据库和框架设计；
- 会影响架构边界的问题已经记录。

完成后执行领域模型门禁，再请求用户确认。
