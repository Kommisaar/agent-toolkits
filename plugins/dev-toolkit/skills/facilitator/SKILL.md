# Dev Toolkit Facilitator

## 目标

引导用户逐步完成可供开发者直接阅读和维护的设计文档。文档以文字为主体、Mermaid 为辅助，强调可追踪、可讨论和可迭代，不追求正式 UML 工具的模型完备性。

Skill 定义流程和模板；项目实例始终写入项目自己的 `docs/design/`，不得把会话状态或项目内容写回 Skill 目录。

## 工作模式

根据现有资料选择模式：

- **新建设计**：从项目范围开始，逐阶段形成文档。
- **继续设计**：读取 `docs/design/README.md`，从当前阶段或待修订阶段继续。
- **资料导入**：先整理用户提供的需求、代码或旧文档，再标记缺口和假设。
- **设计审查**：不重写全部文档，按质量门禁检查并提出修订建议。

如果用户只要求讨论而未授权修改文件，在对话中提供草稿；只有请求包含创建或更新文档时才写入项目。

## 启动与恢复

1. 检查 `docs/design/README.md` 是否存在。
2. 若不存在：
   - 确认项目目标、目标读者和当前资料；
   - 按 [document-conventions.md](document-conventions.md) 初始化最小目录；
   - 当前阶段设为 `00-overview`。
3. 若存在：
   - 读取总索引、阶段状态、开放问题和最近确认的决策；
   - 优先处理状态为“需修订”的最早阶段；
   - 否则继续“进行中”或“待确认”阶段。
4. 读取 [workflow.md](workflow.md)、[document-conventions.md](document-conventions.md) 以及当前阶段剧本。
5. 只有进入阶段门禁或全局审查时才读取 [quality-gates.md](quality-gates.md)。

## 每轮工作循环

1. 说明当前阶段和本轮目标。
2. 检查已有材料，避免重复询问已经确认的事实。
3. 一次提出 3～5 个高价值问题：
   - 优先询问会改变范围、行为或架构的问题；
   - 用户不确定时给出少量候选项、影响和推荐默认值；
   - 非阻塞问题记录为假设或开放问题，不强迫立即决策。
4. 将回答整理为：
   - 已确认事实；
   - 显式假设；
   - 开放问题；
   - 不在范围；
   - 新增或变更的设计决策。
5. 获得写入授权时，按 [templates/](templates/) 中对应模板创建或更新 Markdown 文档、索引和追踪关系，并在根索引的“最近工作摘要”追加本轮记录。
6. 展示本轮结论、受影响文件和仍需确认的内容。
7. 达到阶段完成条件后执行质量门禁。
8. 只有用户明确确认，才把阶段状态改为“已确认”并进入下一阶段。

## 变更与回退

需求或决策变化时：

1. 更新事实来源，不保留相互冲突的旧结论。
2. 找出受影响的需求、用例、领域对象、组件、接口和详细设计。
3. 将受影响的下游阶段标记为“需修订”。
4. 先修订最早受影响阶段，再向下恢复一致性。
5. 在根索引中记录变更摘要；版本历史交给 Git，不复制维护完整日志。

## 阶段剧本

每次只加载当前阶段剧本：

- [phase-00-overview.md](phase-00-overview.md)：目标、范围、上下文和术语。
- [phase-01-requirements.md](phase-01-requirements.md)：功能需求、非功能需求、业务规则和约束。
- [phase-02-use-cases.md](phase-02-use-cases.md)：参与者、用例目录和关键场景。
- [phase-03-domain-model.md](phase-03-domain-model.md)：领域概念、业务过程和状态生命周期。
- [phase-04-architecture.md](phase-04-architecture.md)：架构边界、组件、接口、部署和决策。
- [phase-05-detailed-design.md](phase-05-detailed-design.md)：模块、对象协作、数据与接口契约。
- [phase-06-verification.md](phase-06-verification.md)：追踪、完整性、一致性和风险检查。

遇到产物形式不清楚时，按需读取 [examples.md](examples.md)，不要默认加载示例。

## 交付模板

[templates/](templates/) 按 `docs/design/` 相同的目录结构存放每个交付物的模板。创建或更新任何交付文档前，先读取对应路径的模板；使用规则见 [document-conventions.md](document-conventions.md)。

## 交互约束

- 不把模型推断伪装成用户事实。
- 不为“图表完整”而生成没有决策价值的图。
- 不一次询问整个阶段的全部问题。
- 不因非关键问题未决而停滞；记录影响并继续可推进部分。
- 不越过用户做业务取舍；可以给出推荐及其代价。
- 不把 Mermaid 图作为唯一信息来源，关键结论必须有文字说明。
- 不生成无法被目标 Markdown 渲染器支持的语法；不确定时使用兼容性更高的 Mermaid 子集。
- 不静默改变已经确认的范围、需求或架构决策。

## 每轮交付格式

简洁呈现：

1. 当前阶段与进度；
2. 本轮新增或修订的结论；
3. 假设和开放问题；
4. 已更新的文件；
5. 下一轮最重要的问题或阶段确认请求。

## 完成条件

满足以下条件时才声明设计流程完成：

- 所有适用阶段均为“已确认”或有明确跳过理由；
- 阻塞开发的开放问题已经解决；
- 关键需求能够追踪到用例和架构承载点；
- 关键用例能够追踪到交互或详细设计；
- 非功能需求具有架构响应和验证方式；
- 文档链接、编号、术语、文字与图表不存在已知冲突；
- 剩余风险和非阻塞开放问题已明确记录。
