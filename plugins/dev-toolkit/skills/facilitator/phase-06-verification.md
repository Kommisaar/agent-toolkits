# 阶段 06：验证

## 阶段目标

验证从项目目标、需求、用例、领域模型、架构到详细设计是否完整、一致、可追踪，并判断当前基线是否足以进入开发。

本阶段不以增加新设计为目标。发现缺口时，回到最早负责该问题的阶段修订，再重新验证受影响链路。

## 进入阶段前

读取：

- `docs/design/README.md` 和全部阶段索引；
- `docs/design/open-questions.md`；
- 需求、用例、领域、架构和详细设计中的稳定编号；
- 架构决策和风险；
- `quality-gates.md`。

只读取追踪所需的具体子文档，避免无目的加载全部内容。

## 验证顺序

### 1. 阶段状态

- 是否存在仍为“进行中”或“待确认”的必要阶段？
- “已跳过”的阶段是否有明确理由？
- 是否有“需修订”阶段尚未恢复？
- 设计基线范围和版本是否明确？

### 2. 开放问题

- 是否仍有标记为阻塞的问题？
- 已解决问题是否同步更新受影响文档？
- 非阻塞问题是否说明影响和最晚决策点？
- 是否存在散落在文档中但未进入统一清单的问题？

### 3. 正向追踪

从需求向实现方向检查：

- 每个首期 `FR-*` 是否对应 `UC-*` 或明确的其他承载方式？
- 每个关键 `UC-*` 是否使用明确的 `DOM-*` 并由 `CMP-*` 承载？
- 高风险 `UC-*` 是否具有 `SEQ-*`、模块或接口详细设计？
- 每个关键 `NFR-*` 是否对应组件、ADR、部署策略或验证方式？
- 每个硬约束 `CON-*` 是否在架构和详细设计中得到遵守？

### 4. 反向追踪

从设计向需求方向检查：

- 每个重要组件为什么存在，承载哪些需求或质量属性？
- 每个重大 ADR 的驱动因素是什么？
- 每个公开接口服务于哪些用例？
- 每项复杂详细设计是否解决了已知风险，而非无依据增加复杂度？
- 是否出现没有需求来源的“镀金设计”？

### 5. 语义一致性

- 同一术语在不同文档中的定义是否一致？
- 用例结果是否允许领域状态图中的对应转换？
- 组件职责是否与数据所有权一致？
- 时序图消息方向是否与接口提供方、使用方一致？
- ER 或数据设计是否能维护领域不变量？
- 错误、重试和补偿语义在用例、架构和详细设计中是否一致？
- 权限规则是否在入口、组件和接口设计中一致？

### 6. 文档完整性

- 根索引和阶段索引是否只链接存在的文件？
- 相对链接和锚点是否有效？
- 编号是否唯一，废弃编号是否仍被错误引用？
- Mermaid 代码块是否使用目标渲染器支持的语法？
- 图表和邻近文字是否冲突？
- 是否存在只有图、没有文字结论的重要设计？

## 修订循环

发现问题时：

1. 定位最早负责该事实或决策的阶段。
2. 将该阶段及受影响下游阶段标记为“需修订”。
3. 更新开放问题或对应文档。
4. 用户确认修订后，重新检查受影响追踪链路。
5. 不因局部修订重复审查完全无关的部分。

## 完成判断

可以建议确认最终基线的条件：

- 必要阶段均已确认或有明确跳过理由；
- 阻塞开发的开放问题为零；
- 关键需求、用例、组件、接口和详细设计可追踪；
- 非功能需求具有设计响应和验证方式；
- 没有已知语义冲突、无效链接或重复编号；
- 风险已缓解、接受或具有可执行计划；
- 用户理解未覆盖范围和剩余非阻塞问题。

用户确认后：

- 将阶段 06 和根设计状态改为“已确认”；
- 在根索引记录设计基线摘要和下一步；
- 不自动创建实现任务，除非用户另行要求。
