# 质量门禁

## 使用方式

质量门禁用于发现缺口，不用于追求形式上的满分。

检查结果分为：

- **阻塞**：会导致范围、行为或实现方向无法确定，解决前不能确认阶段。
- **风险**：可以继续，但必须记录影响、临时假设或处理计划。
- **建议**：提升可读性或完整性，不影响阶段推进。

执行阶段门禁时：

1. 只检查当前阶段及其与上游的接口。
2. 给出具体证据和受影响编号，不使用笼统评价。
3. 能直接修正的文档问题，在获得写入授权后修正。
4. 需要业务或架构取舍的问题写入开放问题。
5. 门禁通过后将阶段设为“待确认”，由用户决定是否确认。

## 00 项目概览门禁

- 项目目标说明了要改善的业务结果，而不只是技术实现。
- 目标用户和主要利益相关者已识别。
- 系统边界能够区分系统责任与外部责任。
- 范围和至少一项明确的非范围已记录。
- 关键外部系统、法规、时间、预算或技术约束已记录。
- 术语不存在会改变需求理解的歧义。
- 成功标准能够被观察或判断。

阻塞示例：

- 不同参与者对项目目标存在冲突。
- 核心能力属于本系统还是外部系统尚未确定。
- 首期范围无法区分必须交付与未来设想。

## 01 需求门禁

- 每条需求只有一个主要意图，并具有稳定编号。
- 功能需求描述可观察行为，不预设不必要的技术方案。
- 非功能需求具有度量值、阈值或明确判断方法。
- 业务规则与功能步骤分开记录并可被引用。
- 约束具有来源，避免把偏好写成硬性约束。
- 需求具有优先级、版本范围或明确延期状态。
- 需求之间不存在未解释的冲突。
- 关键需求具有验收依据。

阻塞示例：

- 同一场景要求互斥行为。
- 安全、合规或数据保留要求完全未知且会改变架构。
- 首期必须实现的需求无法确定。

## 02 用例门禁

- 每个用例表达一个参与者目标，而不是页面、按钮或内部函数。
- 参与者代表角色或外部系统，不代表具体个人。
- 关键用例具有触发、前置条件、主流程和成功结果。
- 重要备选流程、异常流程和权限失败已覆盖。
- 系统行为与参与者行为清楚区分。
- 首期功能需求可追踪到至少一个用例，或注明其他承载方式。
- 用例之间的包含、扩展或复用关系具有实际价值。
- 图表和用例规约没有相互矛盾。

阻塞示例：

- 核心业务场景没有明确参与者或完成结果。
- 权限主体不清楚，无法确定谁能执行关键操作。
- 失败后的业务状态无法判断。

## 03 领域模型门禁

- 核心概念来自业务语言，而不是框架、控制器或数据库实现。
- 概念名称与术语表、需求和用例一致。
- 关系具有业务含义，重要基数或所有权已说明。
- 关键业务不变量能够定位到对应概念或规则。
- 复杂生命周期具有状态、转换条件和禁止转换。
- 用例中的主要业务对象能够在领域模型中找到。
- 没有把候选领域模型误写成已确定的数据表设计。

阻塞示例：

- 同一术语在不同场景代表不同实体且未区分。
- 关键状态转换缺少唯一业务规则。
- 业务对象的身份或所有权无法确定。

## 04 架构门禁

- 架构目标明确对应关键质量属性和约束。
- 每个组件具有清晰责任、边界和拥有的数据。
- 关键用例能够定位到负责组件及其协作关系。
- 外部依赖、接口方向和失败影响已说明。
- 身份、授权、敏感数据和信任边界已考虑。
- 部署拓扑足以解释运行单元、存储和外部服务。
- 关键非功能需求具有架构响应和验证思路。
- 重大技术取舍具有 ADR，不只记录结论。
- 不存在明显循环依赖或职责重复而无说明。

阻塞示例：

- 关键数据没有明确所有者。
- 跨边界一致性、安全或故障处理策略缺失。
- 架构选择与硬性约束冲突。

## 05 详细设计门禁

- 详细程度与风险匹配，高风险路径优先于普通样板代码。
- 模块内部职责没有突破已确认的架构边界。
- 公开接口定义输入、输出、错误、权限和幂等要求。
- 关键交互说明正常、失败、超时和重试行为。
- 数据设计说明身份、约束、生命周期和一致性要求。
- 状态变化与领域模型一致。
- 事务边界、并发冲突或最终一致性策略按需说明。
- 可观测性和故障诊断要求覆盖关键路径。
- 设计能够被开发者分解为实现任务，且没有关键语义空白。

阻塞示例：

- 跨组件写入没有一致性策略。
- 公开接口的错误语义会导致调用方无法正确恢复。
- 关键并发场景可能破坏业务不变量。

## 06 验证门禁

- 所有适用阶段均为“已确认”或具有已确认的跳过理由。
- 阻塞开发的开放问题为零。
- 文档入口、相对链接和阶段索引有效。
- 稳定编号没有重复、复用或无来源引用。
- 术语在需求、图表、接口和数据设计中一致。
- Mermaid 图与邻近文字不存在已知冲突。
- 风险具有规避、降低、转移、接受或继续调查的结论。
- 设计基线和剩余非阻塞问题已由用户确认。

## 最小追踪规则

至少检查以下关系：

- `FR-* → UC-*`：功能需求由场景承载。
- `NFR-* → CMP-* / ADR-* / 验证方式`：质量要求具有设计响应。
- `UC-* → DOM-*`：场景使用的关键业务概念存在。
- `UC-* → CMP-*`：场景具有架构承载点。
- `UC-* → SEQ-*`：高风险交互具有详细说明。
- `CMP-* → INT-*`：跨组件协作具有接口。
- `ADR-* → FR-* / NFR-* / CON-*`：架构决策具有驱动因素。

不是每个条目都必须拥有所有关系。缺失关系必须能够解释，例如纯文档需求、组织流程或无需详细时序的简单查询。

## 全局一致性检查

每次上游变化后检查：

- 同一个编号是否在不同文件中表达不同内容；
- 已废弃需求是否仍被用例或设计引用；
- 图表节点名称是否与正文和术语表一致；
- 接口方向是否与时序图消息方向一致；
- 数据所有权是否与组件职责一致；
- 状态图是否允许用例中描述的转换；
- 非功能目标是否被后续技术选择削弱；
- 开放问题解决后是否更新了所有受影响文档。
