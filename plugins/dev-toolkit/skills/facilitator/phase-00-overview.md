# 阶段 00：项目概览

## 阶段目标

建立后续设计共同依赖的上下文：项目为什么存在、服务谁、系统边界在哪里、成功如何判断。

不要在此阶段讨论类、数据库表、框架或部署细节，除非它们是已经确定的外部约束。

## 进入阶段前

优先读取：

- 用户提供的项目简介、需求草稿或旧系统资料；
- 仓库根 README 和已有业务文档；
- 已存在的 `docs/design/00-overview/`；
- 根开放问题中来源为本阶段的条目。

如果资料来自代码，只能把可观察结构当作现状证据，不能据此推断业务目标已经确认。

## 访谈顺序

每轮选择最有价值的 3～5 个问题，不要一次问完。

### 第一组：动机与结果

- 当前要解决的具体问题是什么？
- 谁最直接受到该问题影响？
- 如果项目成功，业务或用户行为会发生什么变化？
- 哪些指标、事件或反馈可以证明有效？
- 如果不做，主要损失或风险是什么？

### 第二组：用户与利益相关者

- 主要用户角色有哪些？
- 谁提出需求、谁使用、谁运营、谁审批或承担风险？
- 不同角色的目标是否冲突？
- 是否存在外部组织、合作方或监管方？

### 第三组：范围

- 首期必须支持哪些能力？
- 明确不做哪些能力？
- 哪些内容属于未来设想而非当前承诺？
- 哪些责任由外部系统或人工流程承担？

### 第四组：环境与约束

- 系统与哪些外部系统交换信息？
- 是否有必须沿用的平台、协议、数据或基础设施？
- 是否存在法规、安全、隐私、地域或审计要求？
- 时间、预算、团队技能或运维能力有哪些硬约束？

### 第五组：术语

- 哪些业务词容易产生歧义？
- 相似概念之间有什么明确区别？
- 是否存在行业内约定但开发者不熟悉的含义？

## 用户不确定时

- 用候选边界帮助用户比较，不替用户决定。
- 将“当前猜测”写为假设，并说明会影响哪些后续阶段。
- 首期范围不清时，优先用“必须 / 应该 / 可以 / 暂不”进行粗分。
- 成功指标暂时无法量化时，先记录可观察现象和后续补充点。

## 产物

按内容规模创建：

- `docs/design/README.md`
- `docs/design/open-questions.md`
- `docs/design/00-overview/README.md`
- `docs/design/00-overview/scope.md`
- `docs/design/00-overview/system-context.md`
- `docs/design/00-overview/glossary.md`

内容较少时，先全部放在阶段 `README.md`（模板：[templates/00-overview/README.md](templates/00-overview/README.md)），达到拆分条件再迁移。

## 系统上下文图

默认使用 Mermaid flowchart，骨架见 [templates/00-overview/system-context.md](templates/00-overview/system-context.md)。

图中只放系统级参与者和外部依赖，不展开内部组件；图后逐个说明外部实体的责任、交互数据或目的、流程与数据归属方，以及尚未确定的边界。

## 阶段完成判断

准备进入门禁前确认：

- 项目目标不是单纯技术动作；
- 主要用户、利益相关者和外部系统已识别；
- 当前范围、非范围和未来候选可区分；
- 系统责任边界足以开始需求分析；
- 关键约束和术语已经记录；
- 未决问题都具有影响说明。

完成后将阶段设为“待确认”，展示摘要并请求用户确认。用户确认后再设为“已确认”。
