# 建模工作流

## 工作流原则

阶段用于控制认知顺序和交付质量，不是不可回退的瀑布流程。允许先形成可用草稿，再随着新事实回到上游修订。

始终遵循：

- 先确认“为什么做、为谁做、边界是什么”，再设计“怎么实现”。
- 分析阶段描述业务事实，设计阶段描述技术选择。
- 每个阶段只解决该阶段应负责的问题。
- 阶段状态反映确认程度，而不是文件是否存在。
- 不适用的阶段或产物可以跳过，但必须记录理由。

## 阶段状态

每个阶段使用以下一种状态：

- **未开始**：尚未进入。
- **进行中**：正在访谈、整理或修订。
- **待确认**：产物已达到门禁要求，等待用户确认。
- **已确认**：用户已确认阶段基线。
- **需修订**：上游变化使原确认内容可能失效。
- **已跳过**：经确认不适用于当前项目，并记录理由。

根 `docs/design/README.md` 至少记录：

- 当前工作模式；
- 当前阶段；
- 各阶段状态；
- 设计基线与关键决策；
- 阻塞问题；
- 最近工作摘要；
- 下一步。

## 00：项目概览

回答“为什么建设这个系统，它处于什么环境中”。

主要产物：

- 项目目标与成功标准；
- 范围和非范围；
- 利益相关者；
- 系统上下文；
- 约束与术语。

退出条件：

- 目标和目标用户清晰；
- 系统边界可解释；
- 关键外部系统已识别；
- 主要约束和术语已记录；
- 不存在会阻止需求分析的范围歧义。

## 01：需求

回答“系统必须提供什么能力，以及必须达到什么质量”。

主要产物：

- 功能需求；
- 非功能需求；
- 业务规则；
- 外部与技术约束；
- 验收依据。

退出条件：

- 需求具有稳定编号；
- 每条需求可验证且来源明确；
- 优先级或首期范围明确；
- 关键非功能需求可度量或至少有可判断标准；
- 冲突和缺失已处理或登记。

## 02：用例

回答“谁在什么条件下，通过系统实现什么目标”。

主要产物：

- 参与者目录；
- 用例目录；
- 关键用例规约；
- 主流程、备选流程和异常流程；
- 用例与需求的关系。

退出条件：

- 首期功能需求均有用例或明确的非用例承载方式；
- 关键用例具有触发条件、前置条件和完成结果；
- 重要失败路径已覆盖；
- 系统责任与参与者责任没有混淆。

## 03：领域模型

回答“业务世界中有哪些概念、规则、过程和状态”。

主要产物：

- 领域概念及关系；
- 核心业务过程；
- 聚合或业务边界候选；
- 关键对象状态生命周期；
- 领域术语与需求、用例的对应关系。

退出条件：

- 名称与术语表一致；
- 模型表达业务概念而非数据库表或框架类；
- 关键业务不变量已记录；
- 用例中的主要业务对象能在模型中找到；
- 复杂状态变化已有文字规则或状态图。

## 04：架构

回答“系统由哪些技术责任单元组成，它们如何协作和部署”。

主要产物：

- 架构目标与质量属性响应；
- 系统、容器或模块边界；
- 组件责任与依赖；
- 外部和内部接口；
- 部署视图；
- 架构决策记录。

退出条件：

- 关键用例有明确架构承载点；
- 组件责任单一且边界可解释；
- 关键非功能需求具有架构响应；
- 外部依赖、信任边界和故障边界已识别；
- 重大取舍通过决策记录说明。

## 05：详细设计

回答“开发者如何实现关键模块和高风险交互”。

主要产物：

- 模块内部职责；
- 设计类、接口和数据结构；
- 关键交互时序；
- API 或消息契约；
- 持久化与一致性策略；
- 错误处理和边界情况。

退出条件：

- 高风险、高复杂度和跨边界路径具有可实现设计；
- 公开接口有明确输入、输出和错误语义；
- 关键状态与事务边界清晰；
- 详细设计与架构边界一致；
- 没有为了完整而提前设计普通样板代码。

## 06：验证

回答“从需求到详细设计是否完整、连贯并足以开始开发”。

主要产物：

- 追踪关系；
- 一致性检查结果；
- 风险清单；
- 剩余开放问题；
- 可实施性结论。

退出条件：

- 阻塞开发的问题已解决；
- 关键链路具有双向追踪；
- 编号、术语、链接、文字与图表一致；
- 风险具有处理方式或明确接受结论；
- 用户确认当前设计基线。

## 推进规则

正常情况下按 `00 → 01 → 02 → 03 → 04 → 05 → 06` 推进。

允许以下调整：

- 已有成熟资料时，先导入并评估覆盖度，再从最早缺失阶段开始。
- 小型项目可以合并相邻阶段的访谈，但仍分别检查完成条件。
- 没有复杂状态、部署或数据设计时，可以跳过对应产物。
- 架构探索可以提前形成候选方案，但在需求确认前不得标记为最终决策。

## 回退规则

上游变化发生后，按影响标记：

- 范围变化：重新检查所有后续阶段。
- 功能需求变化：重新检查用例、领域模型、架构和详细设计。
- 非功能需求变化：重点检查架构、部署和详细设计。
- 用例流程变化：检查领域状态、组件协作和交互时序。
- 领域规则变化：检查用例、数据设计和详细交互。
- 架构边界变化：检查接口、时序、模块和部署设计。

只有重新通过受影响阶段的门禁后，才能恢复“已确认”状态。
